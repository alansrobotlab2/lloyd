# 23. Entity Definitions & Summaries in the Knowledge Graph

## Context

The knowledge graph (`/api/entity-graph`) currently renders entities as nodes and computes edges between them by detecting cross-entity mentions inside fact text. Clicking a node loads that entity's atomic facts in the side panel, but there is no **overview** — no one-line definition or synthesized summary of *who or what* the node represents. A user staring at a graph of 700+ nodes has to read dozens of raw facts to understand any single node.

This plan adds entity-level definitions and summaries — generated by the 122B LLM from the entity's existing facts, augmented with a DuckDuckGo web search for public entities, stored in the vault, regenerated only when that entity's facts change, and surfaced in the graph UI via hover tooltip (definition) and click-opened detail panel (summary).

Fact-level expansion is out of scope; atomic facts are already short and self-explanatory.

## Design Decisions

- **Scope:** Entity-level only.
- **Authoring:** LLM-generated with human override capability (edits in `-profile.md` persist until the entity's facts change).
- **Storage:** New `{entity}-profile.md` file per entity, co-located with facts. Matches the existing `{entity}-{category}.md` convention; `profile` becomes another category.
- **Regeneration:** Change-triggered — only regenerate when an entity's facts have changed.
- **Web augmentation:** Always augment LLM prompts with DuckDuckGo search snippets, **except** for entities whose facts carry category `preference` or `state` (personal-entity heuristic) — those are fact-only.
- **UI surface:** Tooltip shows definition on hover; side panel shows definition + summary on click.

## File Layout

New file per entity:

```
~/obsidian/facts/Alan/Alan-profile.md
```

```markdown
---
type: profile
entity: Claude Agent SDK
category: profile
definition: "Anthropic's Python SDK for building agents that use Claude via tool-use, MCP servers, and session streaming."
generated_at: "2026-04-18T03:30:00Z"
source_fact_count: 12
source_hash: "a1b2c3..."              # SHA256 of concatenated fact bodies
manually_edited: false                # flip to true to freeze against regeneration
web_searched: true                    # false for personal-heuristic skips
web_sources:                          # URLs fed into the LLM prompt
  - "https://docs.anthropic.com/en/docs/claude-code/sdk"
  - "https://github.com/anthropics/claude-agent-sdk-python"
---

# Summary

The Claude Agent SDK is Anthropic's framework for building agentic applications...
[LLM-generated prose, ~150-300 words, blending in-vault facts with web context]
```

Definition lives in frontmatter (easy to surface in graph tooltips without parsing markdown). Summary lives in the markdown body (easy to read in Obsidian, supports formatting). The `manually_edited` flag lets a user lock a profile — the pipeline skips regeneration when it's true. `web_searched` + `web_sources` record augmentation provenance so you can see which summaries drew on external context.

## Implementation

### 1. New pipeline module — `profile_generator.py`

**Path:** `scripts/memory/next-gen-memory/profile_generator.py`

A new class `ProfileGenerator` with:

- `compute_source_hash(entity_dir: Path) -> str` — SHA256 over the concatenated, sorted fact bodies in all `{entity}-*.md` files (excluding `-profile.md`). Drives change detection.
- `needs_regeneration(entity: str) -> bool` — returns True if `{entity}-profile.md` missing, its `source_hash` differs from current, and `manually_edited` is not true.
- `is_personal_entity(entity_dir: Path) -> bool` — returns True if any fact in the entity's files has `category` of `preference` or `state`. Gates web augmentation.
- `web_augment(entity: str) -> tuple[str, list[str]]` — calls `_http_search(entity, count=5)` (imported from `agent_mcp.http_tools`), optionally follows the top 1-2 results with `_http_fetch` for deeper context, returns `(combined_snippets, urls)`. Returns `("", [])` if personal-heuristic hits or search fails.
- `generate(entity: str) -> dict` — reads all facts for entity, runs `web_augment` (skipped if personal), sends a single prompt to the 122B model (`http://127.0.0.1:8096`, same pattern as `FactExtractor`) asking for strict JSON `{definition: str, summary: str}`. Writes `{entity}-profile.md` atomically, recording `web_searched` and `web_sources` in frontmatter.
- Reuses the model-invocation helper pattern from `fact_extractor.py` so we don't duplicate LLM-client plumbing.

**Prompt shape** (sketch):
> "Given these atomic facts about {entity} and these web search snippets, write (1) a single-sentence definition (≤25 words, what this entity IS) and (2) a coherent summary paragraph (≤300 words). **Prefer in-vault facts over web snippets when they conflict** — facts are authoritative. Return strict JSON."

The "facts win on conflict" instruction in the prompt is the contract that prevents web content from overriding curated vault knowledge.

### 2. Hook into nightly extraction

**File:** `scripts/memory/next-gen-memory/nightly_extraction.py`

Add a new step after Step 4 (index rebuild) in `run_full_extraction`:

```python
# Step 5: Entity profile generation (change-triggered)
log_lines.append("\n[Step 5] Entity Profile Generation")
profiles_generated = self._regenerate_entity_profiles()
log_lines.append(f"  → Generated/updated {profiles_generated} entity profiles")
```

New method `_regenerate_entity_profiles` iterates `FACTS_DIR.iterdir()`, calls `ProfileGenerator.needs_regeneration(entity)` for each, and generates only the changed ones. Change detection uses the entity's own `source_hash`, not the existing file-level `ContentHasher` — because `ContentHasher` tracks *input* documents, whereas profiles depend on *extracted facts* which may change without any input file changing (e.g., after manual fact edits).
