## What those numbers say

**Cutting a third of the advertised names bought one character of index.** 208 → 140 skill lines
(68 names stop being advertised, every one of them a production name — the arm never invents a
skill, and every pruned skill stays on disk and stays loadable by `skills_read`, which is the only
reason a tail query is a deferred-task control rather than an ablation). The `<available_skills>`
block went 11,998 → 11,999 characters, and the reason is in the renderer: `skills.index.budget_chars:
12000` is already saturated by the full library, so removing 68 names-only lines frees budget that
is immediately spent granting descriptions to the survivors. The prefix moved 68 tokens. Prefill
looked like a 5.0k-token saving and is not: `prefetch` renders the turn per query, and the two arms
drew different turns (per-query prefill ranged 6k–35k in both arms), so the CI is the size of the
noise at n=6.

**The tail did not lose anything, and at n=1 that is not a defence of pruning.** The one query
whose expected skill this arm stopped advertising (`smq001`, `morning-brief-and-triage`) still
reached its skill — the model found it through `skills_search` with no description and no index
line. One observation. The deferred-task control is present and reported separately, which is the
clause; whether the tail holds up over all 25 tail queries is the owed run.

**The judge score went down 0.33 on six queries.** Also noise at n=6, recorded because "pruning is
free" is exactly the claim a small n is most likely to get wrong in the flattering direction.

## The tail's membership is derived, so it moves — and where it moved is the finding

`split_by_advertisement` derives the tail from `advertised_skill_names(arm)`, which is parsed off
the arm's own rendered prompt, so the population depends on the 30-day rank that decides the cut.
Summarizing this artifact against the **live** log puts `smq001` in the tail and keeps
`smq076`/`smq077` (`runaway-audio-kill`, ranks 122) and `smq078` (`voice-mode`, rank 90) in the
advertised population; summarizing it against an **empty** log — what a worktree or a fresh
checkout sees — moves `morning-brief-and-triage` into the advertised set and the other three into
the tail (`tail_n` 3). Same records, same flags, different population. The tail is therefore a
property of the run's data root, and this file's table is the live-root reading. Any future pass
must say which root it summarized under, or two honest runs will disagree about which arm lost
which query.

Under the live log the rank is dominated by what the *scheduled fleet* is offered, not by what a
chat turn reaches: `retention-sweep` 4,799, `queue-health-check` 3,571, and the 140th name at
count 1, while `morning-brief-and-triage` — 156 loads-by-read in the item's own 30-day account —
sits at rank 147 with rank count 1 and is the one query the pruned arm loses. So "pruned to the
top 140 by rank" is a **rank-pruned** set, not a usage-pruned one, and it prunes in the wrong
place relative to the usage the item cites. That is a measurement-design finding for the
owed-check ruling, not a reason to keep the arm: the arm's job is to make the question answerable,
and it is now answerable.
